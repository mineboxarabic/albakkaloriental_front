# Catalogue performance — 26 October 2026

## Observed bottleneck

The live `/products` page rendered 590 product cards, 591 images, 1,389 links and 7,760 DOM elements. A single HTTP response contained 2,312,300 decoded HTML bytes. Every matching product was rendered before pagination existed, including interactive retail cart controls.

## Change

Retail and wholesale catalogues now render 24 products per page. Filtering and sorting still run over the entire catalogue before slicing; total result counts, French/Arabic search and all product detail routes remain available. Page links preserve category, brand, query, sort and tag. Search and sort changes reset to page one. Invalid page numbers fall back to page one; out-of-range pages clamp to the last available page. Both the top and bottom of the list provide translated previous/next controls.

Product cards and pagination links disable automatic route prefetch, avoiding speculative detail-page requests while browsing. Prices, stock and customer data retain their existing freshness and authorization behavior; no persistent cache or database changes were introduced.

## Controlled production-build benchmark

Baseline: `6733581` (`main`). Same machine, Next.js production builds, 1,000 synthetic visible products, local HTTP backend with no database or artificial delay. Five sequential full HTML requests per audience. This measures server rendering and response completion, not real-user Core Web Vitals. Bytes below are decoded HTML, not compressed network transfer. First requests may include startup costs; production latency and hosting/database performance can differ.

| Metric | Before | After |
| --- | ---: | ---: |
| Retail rendered cards | 1,000 | 24 |
| Retail decoded HTML | 2,979,182 B | 132,017 B |
| Retail median response | 355 ms | 47 ms |
| Wholesale rendered cards | 1,000 | 24 |
| Wholesale decoded HTML | 4,071,557 B | 134,185 B |
| Wholesale median response | 429 ms | 30 ms |

Initial before samples: retail `[767, 370, 354, 337, 355]` ms; wholesale `[841, 429, 442, 372, 349]` ms. Initial after samples: retail `[359, 86, 46, 47, 41]` ms; wholesale `[43, 30, 30, 33, 29]` ms. A follow-up run while building a separate baseline checkout returned retail median 56 ms and wholesale median 51 ms, with identical HTML sizes.

The HTML shrank by 95.6% for retail and 96.7% for wholesale. There are 97.6% fewer product cards to render/hydrate in the 1,000-product fixture. These percentages do not imply an equivalent improvement in total real-world page load time.

## Verification

- 70 targeted Vitest tests pass: pagination boundaries, complete traversal, malformed/out-of-range pages, Unicode filter URLs, search/sort resets, product cards, catalogue visibility, bilingual catalogue and navigation.
- Five production-browser catalogue tests pass: retail/pro category browsing and translated details; phone Arabic navigation; 1,000-product retail/pro pagination, last page, late-product search, sort-before-slice, filter preservation and mobile width. The large-catalogue tests also verify Arabic pagination at phone width.
- `npm run build` passes (existing unused `COLORS` warning and missing build-time backend configuration warning).
- ESLint passes for every changed source/test/config file.
- Repository-wide `npm run lint` fails on 12 existing `no-explicit-any` errors outside this change, plus 6 existing warnings; reproduced on unchanged `main`.
- Existing `e2e/cart.spec.ts` has three failures, reproduced at the same assertions on unchanged `6733581`: retail post-login add button (two tests) and wholesale quantity text (one test). These failures prevent claiming a passing cart suite; the performance change does not modify authentication, cart actions or quantity rules.

Reproduce:

```bash
npm ci
npm run build
npx playwright install chromium
PLAYWRIGHT_PRODUCTION=1 npx playwright test e2e/catalog-performance.spec.ts e2e/catalog-localization.spec.ts
```

The browser tests start a synthetic backend on port 3091 and the application on port 3090. They do not connect to or change production data. `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` can select an existing Chromium binary. Performance samples are printed and attached to Playwright results; timings are informational, while bounded card counts and browsing behavior are asserted.

## Remaining scope

The backend still returns the full catalogue to the server. Shared layout navigation and product details still depend on that endpoint. Backend query time, authenticated customer traffic and hosted before/after Core Web Vitals have not been profiled here. These changes are prepared for review; they have not been deployed.
